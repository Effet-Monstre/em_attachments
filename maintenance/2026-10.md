### En suspens (aucun correctif disponible dans VitePress 1.x)

- **vite 5.4.21** : GHSA-fx2h-pf6j-xcff (high, contournement de `server.fs.deny` sous Windows), GHSA-4w7w-66w2-5vf9 (moderate, path traversal sur les `.map` des deps optimisées), GHSA-v6wh-96g9-6wx3 (moderate, `launch-editor` sous Windows).
- **esbuild 0.21.5** : GHSA-67mh-4wv8-2f99 (moderate).

Le correctif exige vite 6.4.3 ou plus, alors que VitePress 1.6.4 (dernière stable) dépend de
`vite ^5.4.14`. Seul VitePress 2 (encore en `2.0.0-alpha.20`) passe à une vite corrigée ;
forcer vite par un `overrides` sortirait d'une combinaison supportée. Toutes ces
vulnérabilités touchent le serveur de développement (`npm run docs:dev`), pas le site
statique produit par `docs:build`, et ne concernent pas la librairie Elixir. À reprendre
quand VitePress 2 sera stable.

### Point de décision pour le relecteur

Le lockfile de la librairie n'atteint pas les applications. Les exigences de `mix.exs`
(`req ~> 0.5`, `plug ~> 1.16`, `phoenix ~> 1.8`, `ecto ~> 3.11`) autorisent toujours les
versions vulnérables ; conformément à `ci/tasks/maintenance.md`, elles n'ont pas été
relevées puisque le code n'a pas besoin d'une API plus récente. Le CHANGELOG demande aux
applications de lancer `mix hex.audit` chez elles. Relever `req` à `~> 0.6` (bombe de
décompression, HIGH) serait défendable, mais c'est un choix à faire par un humain.
